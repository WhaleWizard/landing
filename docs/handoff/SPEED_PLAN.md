# План ускорения сайта — сессия 01–02.10.2026

Точка входа для продолжения: `docs/handoff/README.md`. Этот файл — живой план второй задачи владельца
(«сайт сильно лагает, первая загрузка ужасная, мигает HTML-страница перед сайтом; сделать быстро, плавно,
ничего не сломать — в первую очередь на телефоне, iPhone 11 и новее; Meta CAPI и SEO не трогать»).
Находки, обнаруженные по ходу, дописываются сюда же — чтобы ничего не потерялось при обрыве сессии.

### Почему лагает — подтверждённые причины

1. **«Сначала HTML-страница, потом сайт».** На главной статический первый экран — настоящий хиро, но React
   монтируется через `createRoot` и **полностью перестраивает DOM**: картинки и CSS-анимации пересоздаются
   (кит и сферы «прыгают» в начало анимации), одна задача на 576 мс (×4). На страницах услуг, блога и
   остальных статическая оболочка — это **другая карточка** («Загружаем интерактивную версию…»), её
   видно 1–3 секунды, потом появляется настоящий дизайн. Это и есть мигание, о котором пишет владелец.
   LCP `/google-ads/` и `/meta-apps/` (5,3–5,8 с) — потому что настоящий хиро появляется только после
   загрузки всего JS.
2. **`/meta-apps/`: анимации чеков и телефона считает JavaScript**, а не композитор: `motion` крутит
   бесконечные `y/rotate` на главном потоке — 5,4 с процессорного времени за замер, TBT 1,9 с. На живом
   iPhone это постоянный «лаг» страницы.
3. **Главная: сцена космоса** — 2,7 с процессорного времени на пыль (canvas 24 к/с) и параллакс; плюс
   подгонка заголовка (`contentTypography`, 228 мс одной задачей: `getComputedStyle` на каждом символе
   заголовка при эффекте «печатная машинка»).
4. **Паутинка (PlexusBackdrop)** на телефоне — холст во всю секцию, перерисовка 24 к/с в «Услугах»,
   «Отзывах», подвале и блоге. Владелец разрешил заменить её на телефоне более лёгкой анимацией.
5. **Стартовый JS**: в входной чанк попал весь `consent.ts` (24 КБ из 70 КБ) только ради `loadConsent()`
   в очереди заявок; иконки админки едут общим чанком на все публичные страницы (F-116); `motion` —
   21 из 31 КБ не используется на главной.
6. **CSS**: единственная блокирующая таблица — 336 КБ (31 КБ brotli), из них 152 КБ — 584 `@font-face`
   библиотеки шрифтов CMS, которые нужны только когда владелец выбрал такой шрифт.
7. **Картинки**: мобильный LCP главной — фон `sky.webp` (131 КБ, десктопный размер) ; кит 148 КБ стартует
   поздно (preload без высокого приоритета); `/consult/` тянет 857 КБ.

## 1. Очередь работ (по приоритету)

- [x] **B. Первый экран без мигания и без перестройки DOM (все маркетинговые страницы).** Сделано 02.10.
  Генератор рендерит настоящий первый экран теми же React-компонентами (`scripts/ssr-entry.tsx`, `createStaticRouter`,
  `renderToString`), `main.tsx` делает **`hydrateRoot`** — DOM, картинки и CSS-анимации сохраняются. Маркеры на
  `<html>`: `data-ww-first-screen` (маршрут) и `data-ww-prehydrate` (петли на паузе до первого коммита React, снимает
  `HydrationRelease`). Текст для поисковиков без JS — в `#ww-static-shell` после `#root`. Маршруты: `/`, `/meta-ads`,
  `/meta-apps`, `/google-ads`, `/consult`. Проверено в настоящем Chrome (iPhone 12, ×4): ни одного предупреждения

## 2. Найдено по ходу (дописывать)

- `ipwho.is` (гео-проверка согласия) — внешний запрос на первой загрузке; в облаке заблокирован, на проде
  работает. Оставить, но не на критическом пути (уже после первого кадра).
- `NotFound.css` — 26 КБ на страницу 404, грузится только там. Не трогать.
- `meta-app-case-*.jpg` (до 433 КБ) лежат в `public/images`, но код ссылается на `.webp`-копии — JPG не
  грузятся, только занимают место в репозитории. Не удалять без владельца.
- Селективная гидратация React: атрибут на `<html>` снимается при первом коммите корня, а ленивые границы
  (`React.lazy`) гидратируются позже — читать признак «до гидратации» из DOM внутри них нельзя, признак
  приходит через props (`settledEntrance` / `hydrating`). На этом сломалась первая версия B в настоящем Chrome.
- Пауза петель до гидратации не должна касаться элементов, которые появляются из `opacity: 0`
  (`.cds *`, `.ths *`): на `/consult/` сцена оставалась невидимой до JS, и FCP/LCP уезжали на секунду.
- Страница статьи: пререндер был общей карточкой, а не статьёй — закрыто пунктом I. `sanitizeHtml` (DOMPurify)
  в браузере остаётся обязательным (правило трёх санитайзеров): при гидратации React не трогает уже
  очищенный серверный HTML, а при переходах внутри сайта очистка идёт как раньше.
- `dompurify`, загруженный без `window` (Node), молча возвращает строку как есть. Теперь `sanitizeHtml.ts` в
  таком состоянии падает, а не молчит; серверному рендеру окно даёт jsdom.
- `optimizeArticleContentImages` ставил `loading`/`decoding`/`fetchpriority` свойствами, а не атрибутами — в
  jsdom этих свойств нет, и серверный HTML остался бы без ленивой загрузки картинок в тексте. Теперь атрибуты.
- Lighthouse на локальном HTTP/1.1 сервере моделирует очередь из шести соединений: порядок ссылок в `<head>`
  влияет на FCP сильнее, чем на HTTP/2 у Cloudflare. Стили — раньше картинок в любом случае.
- `fetch:articles` и JSONBin из облака недоступны (прокси 403) — сборка честно берёт seed из 13 статей; на
  Cloudflare сборка идёт с живым источником.

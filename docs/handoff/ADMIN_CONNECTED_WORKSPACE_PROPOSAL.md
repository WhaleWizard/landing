# Связанные клиенты, проекты и оплаты — предложение 31.10.2026

Статус: обсуждение с владельцем, интерактивный пример готов и проверен. Изменений кода приложения, D1 и production в этой сессии нет. Владелец отверг набор из 20 разрозненных идей и выделил две: весь проект в одном месте и удобный контроль счетов/оплат как дополнение к существующим разделам. Во время работы добавил обязательный сценарий консультаций и разовых доходов. Реализация выбранного устройства интерфейса пока не согласована.

## Суть

Общая карточка клиента — основа. У клиента могут быть постоянные проекты и разовые услуги. Проект собирает задачи, счета, фактические платежи, материалы, доступы, результаты и историю. Разовая консультация доступна прямо в карточке клиента, без обязательного большого проекта.

Существующие CRM, Клиенты, Финансы, планер/задачи, медиатека и результаты сохраняются. Новый экран проекта показывает связанные записи из этих разделов. Запись меняется один раз; карточка клиента, проект и общие списки показывают один результат.

## Что подтверждено по текущему коду

- `AdminClients.tsx`: клиент связан с `lead_id`, содержит массив услуг, общую абонентку, следующий контакт, договор и папку материалов. У него есть помесячные результаты, заметки и доступы.
- `AdminFinance.tsx`: счета связаны с `client_id`; типы услуги — абонентка, консультация, аудит, настройка, прочее. Есть общие счета, финансовые итоги, расходы и время. Сводка разовых продаж уже существует.
- **Причина разрыва консультаций:** форма «Разовая продажа» явно отправляет `client_id: null` и записывает имя/Telegram в `payer`. Платёж учитывается в финансах, но не образует связанную карточку клиента. Это установленное поведение формы, а не предположение по пустой базе.
- `migrations/0033_finance.sql`: у счета одна сумма, статус и `paid_at`; отдельного журнала частичных поступлений в этой схеме нет. Текущая сводка считает полную сумму оплаченного счёта. Просто дорисовать поле «частично оплачен» без изменения общих расчётов нельзя.
- `crm_tasks` связаны с заявкой (`lead_id`); планер хранит недельные данные. Единой проектной связи для всех этих сущностей пока нет. При реализации сначала определить контракт источника задач и не копировать их между CRM и планером.
- `client_months` хранят результаты по клиенту и месяцу. Исторические результаты нельзя автоматически приписать одному из нескольких новых проектов или продублировать в каждый.

## Предлагаемый сценарий владельца

1. **Список проектов:** поиск по клиенту/названию; сортировка «требуют внимания», по ближайшему делу, по имени. Строка: клиент + направление, следующий шаг и дата, остаток к оплате. Открытие целой страницы проекта.
2. **Обзор проекта:** что делаем, ближайшие задачи, задолженность и срок, следующий согласованный счёт при регулярной услуге, контакт клиента. Подробности в понятных вкладках: Задачи, Счета и оплаты, Материалы, Результаты, История.
3. **Карточка клиента:** потребности, интересующие услуги, заказанные/оказанные услуги, все проекты, фактические поступления за всё время, в том числе разовые, задолженность, следующий контакт. Статус клиента отдельно от статуса каждой услуги.
4. **Консультация:** выбрать существующего клиента или быстро создать карточку по имени и контакту; выбрать услугу/тему, дату, цену и факт оплаты. Проект не обязателен. Повторная консультация, последующий аудит или ведение остаются у того же клиента. Не создавать клиента автоматически только по совпавшему имени.
5. **Контроль оплат в Финансах:** дополнительный режим, а не замена нынешних счетов/итогов/расходов/времени. Фильтры клиент/проект/валюта, просроченные, срок на неделе, оплаченные, все. Сумма счёта, получено, остаток, срок, переход к клиенту и проекту.
6. **Внутри счета:** отдельные фактические поступления с датами, частичная оплата, остаток; напоминание владельцу. Напоминание видно в общем списке дел и в проекте. Автоматическая отправка клиентам не входит в предложение.

Пример: консультация Антона оплачена на 300 USD, аудит на 500 USD лишь обсуждается. В карточке видны оба направления, но фактически получено 300 USD, долга за незаказанный аудит нет.

## Сквозные правила

- Клиент общий; проект принадлежит одному клиенту. Одна услуга/продажа может быть разовой и не иметь проекта.
- У заказа/потребности, этапа оказания услуги, статуса счета и факта поступления денег разные значения. Обсуждаемая услуга не становится доходом или долгом.
- Деньги клиента = фактически полученные платежи. Выставленная сумма, остаток, предложения и рекламный бюджет показываются отдельно.
- «Из них разовые» — часть общего полученного, её не прибавляют повторно. Валюты не суммируются без явно выбранного правила пересчёта; по умолчанию отдельные суммы по каждой валюте.
- Черновики и отменённые счета не входят в долг. Просрочка вычисляется по сроку и ненулевому остатку; нажатие «проведена консультация» не означает «оплачено».
- Напоминания привязаны к исходному счету. При полной оплате открытая задача об этом долге закрывается с сохранением истории; повторное сохранение не размножает её.
- Оплата фиксируется один раз с защитой от двойной отправки/повторного клика. Ошибочная запись исправляется с журналом действий; возврат денег — отдельная операция, не бесследное удаление.
- Переходы из общей таблицы в проект/клиента сохраняют контекст и позволяют вернуться к прежним фильтрам и строке. Полный проект не превращается в бесконечную форму: обзор краткий, подробности по вкладкам.
- Для регулярных услуг подготовка следующего счета должна учитывать проект/услугу, период и вид начисления. Нельзя оставить нынешнюю проверку «один клиент за месяц», если у клиента несколько направлений. Повторный запуск не создаёт дублей.
- Разовые услуги и разовый запуск не получают автоматически следующую месячную абонентку. В примере запуск «Маяка» показан отдельно от ведения.
- Общие документы клиента доступны его проектам по связи. Файлы в R2 не копируются. Доступы отображают состояние предоставления; секреты в сводку не выводятся.

## Как добавить, сохранив существующее

1. Сначала связать быстрые разовые продажи с существующим/новым клиентом; показать в его карточке текущие счета, услуги и сумму фактических поступлений. Не менять историю без однозначной привязки.
2. Добавить проекты и связи с существующими счетами, задачами, временем, материалами, заметками, результатами. Клиентские данные без проекта остаются в разделе «Общее по клиенту / не распределено» до выбора владельца.
3. Добавить экран проекта и двусторонние переходы из CRM, Клиентов, Финансов и связанных задач. Проверить переход консультация → аудит → проект ведения без повторного создания клиента.
4. Добавить журнал поступлений и контроль оплат. Одновременно обновить все затронутые финансовые сводки и клиентские суммы, чтобы частичные платежи не считались иначе в разных разделах.
5. Добавить внутренние напоминания и аккуратный цикл регулярных начислений. Использовать общие записи, без двух копий задачи.

Миграции D1 — только расширение схемы после утверждения реализации. Возможные сущности: проекты/заказы услуг, поступления по существующим счетам, связи задач/материалов, напоминания. Окончательную структуру выбирать после проверки всех действующих контрактов. Не переписывать всю БД ради сетки интерфейса.

Перенос старых оплаченных счетов в журнал поступлений должен быть идемпотентным; одну историческую сумму нельзя учитывать и по статусу, и по новой записи. Если дата оплаты неизвестна, не придумывать её и не относить поступление к произвольному месяцу. Старые консультации с одним `payer` показать отдельным списком для ручной привязки, не сливать по имени. Резервная копия/план отката и проверки до применения миграций обязательны на этапе реализации.

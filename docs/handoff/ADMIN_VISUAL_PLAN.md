# План визуальной переработки всей админки

Дата старта: 30.10.2026. Рабочая ветка при старте: main, дерево чистое. Мастер-промпт: [ADMIN_VISUAL_MASTER_PROMPT.md](ADMIN_VISUAL_MASTER_PROMPT.md).

## Цель и статус

**Уточнение владельца в этой сессии: сначала только основная тёмная ПК-версия.** Главный критерий — отображение текста: достаточная ширина, читаемые строки и поля, строгая аккуратная сетка, отсутствие наложений, прыжков и переносов по одному слову/символу. Светлую и мобильную версии отложить. Памятка — [ADMIN_VISUAL_MOBILE_LIGHT_FOLLOWUP.md](ADMIN_VISUAL_MOBILE_LIGHT_FOLLOWUP.md). Ниже перечислен полный первоначальный охват; мобильная/светлая приёмка сейчас не является текущим этапом.

Единый спокойный рабочий интерфейс во всех разделах: согласованные размеры и сетки, чистая типографика, ровные списки и таблицы, удобные формы и редакторы, отсутствие наложений и недоступных действий.

**30.10.2026: основная тёмная ПК-версия завершена и выложена (6934b6e, Cloudflare Pages success).** Все 23 раздела и существенные вложенные состояния просмотрены в рамках coverage.json; 26 desktop-находок исправлены, AV-04 относится к отложенной светлой теме. Финальный npm run check = 0, production admin CSS совпадает с проверенной локальной сборкой. Автоматизация whale-wizard удалена. Границы проверки ниже и в checkpoint; мобильная/светлая работа — отдельный этап.

## Что уже установлено по исходникам

- Фактическая навигация в Admin.tsx содержит 23 раздела, хотя вводное описание AGENTS.md ещё говорит о 18.
- Существуют AdminUI, AdminFeedback, общие токены, тёмная/светлая темы и просторная/плотная компоновка. Их следует развивать последовательно.
- admin-ui.css и отдельный admin-theme.css содержат большие пересекающиеся слои геометрии и декоративных эффектов. Наличие нескольких слоёв — основание проверить каскад, само по себе не доказательство конкретного дефекта.
- Локальный Vite не воспроизводит полноценные D1/R2-разделы. Production нужен для исходного осмотра; проверка правок должна отдельно обеспечить реалистичные заполненные и пустые состояния без изменения production-данных.

## Этапы

### 0. Исходное состояние и полный обход — выполнен для текущего scope

1. Сверить навигацию production с 23 пунктами исходников.
2. Снять все разделы сверху вниз на рабочем desktop-размере; проверить основные вложенные режимы и безопасные открытые состояния.
3. Составить findings.json с приоритетами: P1 — наложение/невозможность действия; P2 — плохая читаемость, иерархия, сетка; P3 — визуальная несогласованность.
4. Оценить обе темы, плотности, длинные подписи и ширины окна. Зафиксировать пустые и недоступные состояния отдельно от заполненных.
5. Завершить baseline-check и отделить старые ошибки от появившихся при правках.

Результат: coverage.json, findings.json, локальные скриншоты before. Каждая находка имеет экран и воспроизводимое состояние.

### 1. Общая система и оболочка — выполнено для тёмного desktop

- Размеры sidebar/topbar/контентной области, выравнивание заголовков и действий, липкие панели и поведение при прокрутке.
- Стандарты полей, кнопок, селектов, вкладок, карточек, таблиц, подсказок, иконок и статусов через существующие компоненты и токены.
- Визуальные уровни: фон → рабочая поверхность → поле; единый смысл акцента, минимально необходимый декор.
- Обе темы, порталы вне .admin-root, 2 режима плотности, reduced motion.

Результат: проверенные общие компоненты и контрольные сложные экраны. Параметры корректируются по реальным замерам; не утверждать произвольные размеры заранее.

### 2. Ежедневная работа и CRM — выполнено в текущем scope

Сегодня → Планер → Чек-листы запуска → Заявки → Клиенты. Карточки дня, неделя, поля ввода, списки задач, фильтры, таблицы и доска, карточки сделки/клиента, панели действий. Пустые production-разделы дополнить изолированными локальными фикстурами для проверки длинных значений и заполненных строк.

### 3. Деньги, аналитика и диагностика — выполнено в текущем scope

Финансы → Цели и деньги → Юнит-экономика → Воронка → SEO и Поиск → Meta CAPI → События → Скорость → Отчёт за месяц. Табличные суммы и единицы, периоды, графики и легенды, предупреждения и раскрывающиеся детали. Проверить печать отчёта и читаемость плотных показателей.

### 4. Контент и редакторы — выполнено в текущем scope

Статьи → Кейсы → Редактор сайта → Медиатека. Список/витрина, сортировки и фильтры, быстрые действия, календарь, расписание, блочный редактор, редактор Markdown, split-preview, параметры строк заголовков, выбор шрифтов/цветов, diff/история, файловые карточки и боковые панели.

Это отдельный подробный проход: новые настройки не должны превращаться в тесную строку; контент, параметры и предпросмотр должны иметь ясную иерархию.

### 5. Система и общие диалоги — выполнено в текущем scope

Уведомления → Журнал аудита → Доступ к страницам → Миграции → Проверка. Сводки, статусы, фильтры, сообщения о настройке, раскрытые детали. Также Ctrl+K, справка клавиш, диалоги подтверждения и повторного входа (без выхода из текущей сессии и без изменения защиты).

### 6. Сквозная приёмка ПК-версии — локально выполнена с указанными пределами

- Для всех 23 разделов: основная тёмная тема на desktop, повторный осмотр после общих CSS-правок.
- Рабочие desktop-размеры: 1280/1440/1920; 1024 как узкое окно ПК. Особое внимание длинным русским названиям, широким таблицам, настройкам строк и раскрытым редакторам.
- Для общих компонентов и самых плотных экранов: масштаб 125/150/200% в пределах desktop-сценария, обе плотности, клавиатура, focus-visible, Escape, восстановление фокуса, длинные значения и пустые состояния. Подробный мобильный и светлый проход отложен владельцем.
- Для таблиц/канбана допускается только управляемая локальная горизонтальная прокрутка. Проверить отсутствие случайного скролла страницы и перекрытия sticky-панелями.
- Проверить открытые меню/попапы у краёв экрана, скролл диалогов и видимость нижних действий.
- По существующим сценариям: импорты админки, оболочка, CRM, редакторы; полный npm run check перед готовностью/выкладкой. Трекинг не изменять; при изменении выполнить отдельный осознанный test:meta-capi.
- Показать сопоставимые до/после. Все непроверенные сценарии и блокеры указать явно. Не подтверждать сохранение на production по одному визуальному осмотру.

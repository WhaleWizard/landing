## Что нужно сделать один раз

### 1. Миграции D1

✅ **Выполнено 17.07 и 23.07.2026** — применены все миграции до `0020` включительно.

Cloudflare Dashboard → Storage & Databases → D1 → база сайта → вкладка **Console**. Примените все ещё не применённые файлы из `migrations/` строго по номеру. В частности:

- `0012` — базовая воронка и история действий;
- `0013` — черновики и опубликованные тексты сайта;
- `0014` — полноценное рабочее место CRM, задачи, заметки и теги;
- `0015` — долговечная квитанция согласия для отложенных событий качества лида;
- `0016` — автоматическое удаление диагностики Meta старше 90 дней;
- `0017` — ограничения и целостность CRM;
- `0018` — атомарный D1-журнал использованных nonce и агрегированная диагностика подписей;
- `0019` — устойчивый журнал приёма заявок и дедупликация повторов по `event_id`.

Миграции с `ALTER TABLE` одноразовые: перед применением сделайте экспорт production D1 и не запускайте один и тот же файл повторно.
`0019` примените до новой версии `/api/lead` или в том же окне обслуживания до
поступления трафика: без таблицы `lead_ingestions` endpoint намеренно отвечает
повторяемым `503`, чтобы не показывать успех до надёжной записи заявки.

**Проверьте, применены ли** (нужны для разделов «Планер» и «Воронка»). Каждый раздел сам сообщает, какого файла ему не хватает:

- `0021` — недельный планер (если раздел «Планер» открывается и сохраняет неделю, миграция уже применена);
- `0022` — признаки формы (`form_id`, `form_variant`) в заявке. Без неё разрезы «Форма» и «Вариант формы» в воронке остаются выключенными; заявки, оставленные до применения, попадут в строку «Не указано» — задним числом эти данные не восстанавливаются;
- `0023` — таблица `ad_spend` для рекламных расходов, которые владелец вводит вручную в разделе «Воронка». Без неё цена лида, цена целевого лида и ROMI не считаются и не показываются.

### 2. Telegram-секреты (для отправки заявок без Google Apps Script)

1. В @BotFather: `/mybots` → выбрать бота → API Token → **Revoke** (старый токен засвечен) → скопировать новый.
2. Cloudflare Pages → проект сайта → Settings → Environment variables → добавить для Production:
   - `TELEGRAM_BOT_TOKEN` = новый токен (тип Secret)
   - `TELEGRAM_CHAT_ID` = ID чата, куда бот шлёт заявки (тот же, что был в Apps Script)
3. Redeploy. После этого Google Apps Script можно отключить (Deployments → Archive).

Проверка chat_id: если уведомления не приходят, убедитесь, что бот состоит в чате/группе и ID указан со знаком минус для групп.

### 3. Публикация текстов и SEO

Добавьте `CF_PAGES_DEPLOY_HOOK_URL` как Secret и после первого успешного переходного деплоя включите `REQUIRE_FRESH_SITE_CONTENT=true`. Тогда публикация из редактора запускает production-сборку, а сборка останавливается вместо выпуска устаревшего SEO-HTML, если свежий D1-снимок недоступен. Hook только запускает асинхронную сборку: обновление статического SEO-HTML подтверждается её успешным завершением в Cloudflare Deployments.

Для очистки edge-кэша после публикации добавьте `CF_ZONE_ID` как Plaintext и
`CF_CACHE_PURGE_TOKEN` как Secret с минимальным разрешением `Zone.Cache Purge`.
Эти две переменные очищают кэш, но не заменяют deploy hook.

### 4. Остальные биндинги

Медиатека и дашборд работают на существующих биндингах (`BUCKET`, `DB`). Для
Meta нужны KV `META_CAPI_DIAGNOSTICS` и `META_CAPI_IDEMPOTENCY`.
`META_CAPI_NONCE` оставьте подключённым только как совместимый fallback для
`TRACKING_SIGNATURE_MODE=monitor`; атомарную replay-защиту обеспечивает D1
после миграции `0018`. Все admin-эндпоинты защищены `ADMIN_PASSWORD` (заголовок
`X-Admin-Password`) и rate-limit'ом.

`TRACKING_HMAC_SECRET` храните как Secret в формате ровно 64 шестнадцатеричных
символов, `TRACKING_SIG_TTL_SEC=60` — как Plaintext. Режим подписей оставьте
`monitor`, пока доверенный серверный клиент фактически не начнёт подписывать
запросы и production-диагностика не покажет валидные подписи. Включать `enforce`
для текущего браузерного клиента нельзя: общий HMAC-секрет нельзя безопасно
размещать во frontend bundle.

## Качество лидов → Meta (QualifiedLead / UnqualifiedLead)

Кнопки «целевой»/«нецелевой» в разделе «Заявки» отправляют в Meta CAPI события
`QualifiedLead` / `UnqualifiedLead` (`functions/_lib/lead-quality.ts`):

- только если посетитель дал `marketing_consent` вместе с заявкой и в D1 сохранена полная квитанция этого решения;
- квитанция хранит версию, источник, регион, клиентское время решения и серверное время записи; для отложенного CRM-события она действует не более 180 дней — столько же, сколько согласие в браузере;
- PII уходит как SHA-256 хеши (email/phone/external_id) + fbp/fbc клика;
- `action_source: system_generated`, `event_id: lq:<quality>:<lead_id>` — повторные клики дедуплицируются;
- при сбое событие лежит в `meta_outbox` и досылается фоном, статус ответа Meta показывается в админке.

Требуются миграции 0009 (метка quality), 0010 (fbp/fbc/consent-контекст), 0015 (квитанция согласия) и 0019 (идемпотентный приём заявок по `event_id`). Старые заявки без квитанции остаются в CRM, но событие качества для них безопасно пропускается.
Снятие метки событие не отправляет — «отозвать» событие в Meta нельзя.

После первой отметки дождитесь постоянного статуса доставки в админке, затем
найдите событие в Meta Events Manager. Только эта внешняя проверка подтверждает
production-доставку. Custom Conversions и оптимизацию на `QualifiedLead`
настраивайте уже после подтверждения корректных событий и достаточного
стабильного объёма данных; сам локальный или D1-статус этого не гарантирует.

## Поведение без настройки

- Нет нужной миграции → соответствующий раздел админки показывает понятную заглушку и точный номер файла. Без `0019` приём заявок отдельно отвечает retryable `503`, чтобы браузерная очередь могла повторить отправку и заявка не потерялась за ложным `200`.
- Нет Telegram-секретов → заявки идут через старый Apps Script.
- Локальный dev (vite) → функций нет, разделы показывают заглушку.

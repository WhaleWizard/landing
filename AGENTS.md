# AGENTS.md — Landing (whalewzrd.com)

Зеркало `CLAUDE.md` — для инструментов, читающих AGENTS.md (Codex и др.). Меняешь один файл — синхронизируй второй.

## Что это

«Whale Wizard» (whalewzrd.com) — русскоязычный сайт performance-маркетолога: лендинги услуг (Google Ads / Meta Ads / консультации), блог и кейсы на CMS, лид-формы, калькуляторы бюджета и ROI, глоссарий/FAQ, юридические страницы, админка. Фронтенд — React SPA, бэкенд — Cloudflare Pages Functions. Исходно сгенерирован через Figma Make (`ATTRIBUTIONS.md`).

Владелец — маркетолог, не разработчик: админка для него рабочий инструмент, а не витрина возможностей. Отсюда два сквозных правила ниже — «не выдумывать числа» и «раздел без миграции объясняет себя, а не падает».

Git remote: `github.com/WhaleWizard/landing`, ветка по умолчанию `main`.

## Команды

Пакетный менеджер: **pnpm** — источник истины по локфайлу (`pnpm-lock.yaml`). `package-lock.json` тоже закоммичен — это известная несогласованность; не давай им расходиться дальше, для установки используй `pnpm install`.

```
pnpm dev                                 # dev-сервер vite
npm run build                            # fetch:articles && vite build && generate:pages — реальная production-сборка
npm run test                             # алиас npm run build — юнит-тестов приложения нет
npm run check                            # все проверки + сборка — обязательный прогон перед выкладкой
npx -p typescript tsc -p tsconfig.functions.json --noEmit   # типы functions/ (typescript не в devDeps)
```

`npm run check` — это цепочка, а не один тест:

```
test:meta-capi          смоук-тесты Meta CAPI (проверяют строки в исходниках, не поведение)
test:lead-reliability   надёжность приёма заявок
test:tracking-security  подпись и защита tracking-запросов
test:seo-content        синхронизация текстов сайта и статики
test:calculator         движок калькуляторов
test:glossary           целостность глоссария
test:admin-imports      каждый компонент в разметке админки действительно импортирован
build                   production-сборка
test:seo-output         SEO-контракт сгенерированных страниц
```

`test:admin-imports` существует не просто так: типы `src/` нигде не проверяются, поэтому забытый импорт собирается зелёным и падает уже в бою. Это уже случалось.

Чего в проекте НЕТ (не предполагать): lint/ESLint, корневого tsconfig.json (типы проверяются только в `functions/`), CI (`.github/workflows`), мониторинга ошибок (Sentry). Поэтому `npm run check` — основная проверка любой правки; для всего, что касается трекинга (`_lib/meta-*`, `_lib/leads`, `_lib/lead-quality`, `api/meta-*`, `api/lead`, `api/pageview`, consent) `npm run test:meta-capi` обязателен отдельно и осознанно.

## Архитектура

### SPA (src/) и edge-бэкенд (functions/)

- `src/app/` — React 18 + React Router 7. `routes.tsx` — дерево роутов, всё кроме Home лениво через `React.lazy`. `RouteErrorBoundary` ловит устаревшие чанки после деплоя и перезагружает страницу один раз.
  - `components/` — фичи: Hero, Navbar, ContactForm, LandingForm, калькуляторы, Blog, Cases, ArticleEditor (блочный редактор), `admin/` (все разделы админки), SEO.tsx, `cookie/` (баннер согласия), `legal/`, `brand/` (WhaleMark).
  - `components/ui/` — shadcn/ui-примитивы, считать вендорными: не переписывать, следовать их паттернам.
  - `pages/` — по одной на роут; `BlogPage` обслуживает и /blog, и /cases; `Admin.tsx` — оболочка админки.
  - `consent/consent.ts` — ядро трекинга: согласие, загрузка пикселей, track*-функции, сбор контекста для CAPI.
  - `utils/` — sanitizeHtml (DOMPurify для CMS-статей), phoneCountry (коды стран + buildFullPhone), leadRetryQueue (офлайн-очередь заявок в localStorage), compressImage.
  - `styles/admin-ui.css` — все стили админки одним файлом. Импортируется из `Admin.tsx`, а не из глобального `index.css`: иначе его вес попадал бы в блокирующую рендер таблицу стилей каждой публичной страницы.
- `functions/` — Cloudflare Pages Functions, роутинг по файлам. `_middleware.ts` на каждом запросе: 301 с whalewzrd.com на www + security-заголовки/CSP.
- `functions/_lib/` — общая серверная логика (не роутится): `articles`, `auth`, `d1`, `jsonbin`, `leads` (заявки + статистика посещений), `admin-crm`, `admin-alerts`, `admin-lead-quality-status`, `lead-quality` (события качества лида в Meta), `meta-capi`, `meta-diagnostics`, `meta-outbox`, `meta-pii`, `media-folders`, `site-content`, `rate-limit`, `sanitize`, `seo`, `tracking-signature`, `cache`, `http`, `url-sanitize`, `types` (контракт `Env`).
- `wrangler.toml` нет — все биндинги (D1 `DB`, R2 `BUCKET`, KV, секреты) настраиваются в Cloudflare Pages. Полный список — в `README.md` и `.env.example`.

### Статьи: два источника с fallback-цепочкой

Чтение (`_lib/articles.ts`): D1 (если `USE_D1_ARTICLES=true`) → JSONBin → статический `articles.seed.json` из сборки. `REQUIRE_FRESH_ARTICLES=true` валит сборку вместо устаревшего контента; `ALLOW_FALLBACK_BUILD=true` — аварийный обход. Черновики и будущие `publishedAt` отфильтровываются из публичных выдач.

### SEO: три уровня

- `scripts/generate-pages.js` пре-рендерит статический HTML для роутов из `scripts/config.js` (`STATIC_ROUTES`) — при добавлении индексируемого роута синхронизируй этот список с `routes.tsx`.
- `functions/blog/[slug].ts` и `functions/cases/[slug].ts` отдают ботам SEO-HTML статей на лету. Принадлежность к кейсам определяет ТОЛЬКО `isCaseArticle()` из `_lib/seo.ts` — не сравнивать категорию строкой.
- `sitemap.xml` и `feed.xml` генерируются динамически из живого хранилища статей.

### Трекинг: пиксели + серверный Meta CAPI

Meta CAPI и всё, что связано с доставкой и качеством событий Meta, — неприкосновенный приоритет проекта. Любые изменения сайта должны сохранять или улучшать трекинг: передавать для каждого реального события максимум полезных и разрешённых параметров, которые действительно доступны, но не собирать лишние данные, не придумывать сигналы и не отправлять запрещённые чувствительные категории. Обязательны согласие пользователя, корректное хеширование PII, общий `event_id` для дедупликации Pixel/CAPI, outbox-досылка и честная диагностика фактических ответов Meta. Для любых правок трекинга запускать `npm run test:meta-capi` и production-сборку; фактическую доставку после выкладки дополнительно проверять в диагностике сайта и Meta Events Manager.

Клиентские пиксели (GTM, GA4, Метрика, Meta, TikTok) + серверный CAPI (`api/meta-event`, `api/lead`, `api/pageview`), дедупликация с пикселем через общий `event_id`. Версия Graph API — `META_CAPI_API_VERSION` (сейчас v25.0, код менять не нужно при апдейте версии).

Недоставленные события попадают в D1-очередь `meta_outbox` (хранится готовое тело запроса к Graph API) и досылаются: фоном при каждом `/api/pageview` и через `POST /api/meta-outbox-process` (секрет в заголовке `x-meta-debug-secret`) для внешнего cron. «sent» ставится только при успешном ответе Meta. Подробности — `docs/META_CAPI_CLOUDFLARE_SETUP.md`.

Диагностика — `api/meta-diagnostics-*` (KV `META_CAPI_DIAGNOSTICS` / `META_CAPI_IDEMPOTENCY` / `META_CAPI_NONCE` + D1). Серверные события уходят только при `marketing_consent=true` — не ослаблять.

`POST /api/meta-test-event` отправляет событие с `test_event_code` (видно в Events Manager → «Тестирование событий», в живую статистику не попадает). Допуск двойной: секрет `META_CAPI_DEBUG_SECRET` в заголовке `x-meta-debug-secret` **или** пароль админки в `X-Admin-Password` — второй нужен кнопке «Тестовое событие» в разделе Meta CAPI.

### Заявки и первичная статистика

`/api/lead`: заявка валидируется → пишется в D1 `leads` (`_lib/leads.ts`; дедупликация по email/телефону/telegram — повторная заявка поднимает существующую со счётчиком, а не создаёт дубль) → уведомление в Telegram напрямую через Bot API (секреты `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`; если не заданы — fallback на старый Google Apps Script). `storeLead` определяет применённые миграции через PRAGMA и работает при любом их наборе. Признаки формы `form_id`/`form_variant` сохраняются с миграции 0022 — без неё разрезы «Форма» и «Вариант формы» в воронке отключаются, а не показывают нули.

Кнопки «целевой/нецелевой» в админке шлют в Meta CAPI события `QualifiedLead`/`UnqualifiedLead` (`_lib/lead-quality.ts`): только при marketing_consent, сохранённом с заявкой; PII — SHA-256 хеши + fbp/fbc; outbox-досылка и дедупликация по `event_id`. Consent-гейт не ослаблять.

`/api/pageview` дополнительно пишет агрегаты посещаемости в D1 (`page_stats_daily`, `visitor_hashes_daily` — суточный хеш IP+UA+соль, сырые IP/UA не хранятся, хеши чистятся через 90 дней). `/api/vitals` пишет реальные Core Web Vitals посетителей в `web_vitals_daily` — только суточные агрегаты, без визитов и идентификаторов.

## Админка

`/admin` — SPA (`src/app/pages/Admin.tsx`), пятнадцать разделов, компоненты в `src/app/components/admin/`, бэкенд `functions/api/admin/*`.

Аутентификация — общий `ADMIN_PASSWORD` (`_lib/auth.ts`), передаётся в теле или заголовке `X-Admin-Password`, **НИКОГДА в query string**. Пароль живёт только в памяти вкладки: перезагрузка страницы разлогинивает, это ожидаемо.

Загрузки в R2 (`api/admin/upload`): лимит 15 МБ, белый список MIME (JPEG/PNG/WebP/GIF/AVIF/PDF/ZIP/DOCX/XLSX/PPTX); SVG/HTML/JS/XML заблокированы намеренно против stored-XSS — не ослаблять. После сохранения статей кэш чистится локально + глобально через Cloudflare API, если заданы `CF_ZONE_ID` и `CF_CACHE_PURGE_TOKEN`. Настройка разделов — `docs/ADMIN_SETUP_V2.md`, `docs/ADMIN_CONTROL_CENTER_SETUP.md`.

### Оболочка и общие правила интерфейса

- `AdminFeedback.tsx` — единый слой обратной связи: тосты (`notify`) вместо `alert`, свой диалог (`confirmAsk`) вместо `confirm`, скелетоны (`AdminSectionSkeleton`), пустые состояния (`AdminBlank`, по умолчанию рисует кита `WhaleMark`). Ничего из этого не дублировать — переиспользовать.
- `AdminUI.tsx` — `AdminSelect` (системный `<select>` в публичном интерфейсе не считается готовым UI), `AdminButton`, `AdminPanel`, заголовки секций.
- `AdminCommandPalette.tsx` — палитра по Ctrl+K: разделы, действия, поиск по публикациям. Горячая клавиша ловится по `event.code`, а не по `event.key`: на русской раскладке Ctrl+K даёт «л».
- Плотность длинных списков («просторно / плотно») и тема хранятся в localStorage, применяются атрибутами `data-density` и `data-theme` на `.admin-root`.
- Липкие панели внутри разделов отступают от шапки через переменную `--adm-sticky-top`. Не ставить `top: 12px` — панель уедет под шапку.

### Разделы

**Сегодня** (`AdminToday.tsx` + `api/admin/today.ts`) — стартовый экран. «Фокус дня» собирает конкретные дела с именами и сроками: просроченные следующие шаги по сделкам, задачи CRM на сегодня и просроченные, новые заявки, невыполненные задачи планера. Плюс план на день (`TodayPlan.tsx`) со стриком выполнения, заметка дня (`TodayNote.tsx`, пишется в заметки того же дня в планере — своего хранилища у неё нет), цель месяца (`TodayGoal.tsx`), центр уведомлений (`AdminAlerts.tsx` + `api/admin/alerts.ts`), блок «что изменилось со вчера» (считается на клиенте из данных `api/admin/stats`, сравниваются два последних завершённых дня) и топ-3 источника заявок с ценой лида.

**Планер** (`AdminPlanner.tsx`, `plannerModel.ts` + `api/admin/planner.ts`) — неделя хранится одним JSON на строку `planner_weeks`: цели недели, задачи и заметки по дням, трекер привычек, дневник. Автосохранение с досылкой через `sendBeacon` при закрытии вкладки. Шаблон недели — `api/admin/planner-template.ts`: повторяющиеся дела подставляются в пустую текущую или будущую неделю **без сохранения** (пролистывание недель не должно плодить записи в базе). Перенос невыполненного на следующий день; из воскресенья задачи уезжают в следующую неделю — это отдельная строка, поэтому из текущей они убираются только после подтверждённого сохранения соседней.

**Заявки** (`AdminLeads.tsx` + `crm-leads`, `lead-crm`, `lead-trash`, `crm-analytics`, `crm-templates`) — три режима: доска (`CrmBoard.tsx`, смена этапа перетаскиванием или стрелками, оптимистичное обновление с откатом), список и аналитика (`CrmAnalytics.tsx`). Режим хранится в localStorage. Автооценка лида (`leadScore.ts`) считается из данных заявки и **ничего не перезаписывает**: ручной ползунок главный, автооценка предлагается кнопкой и всегда объясняет себя списком причин. Поиск дублей (`leadDuplicates.ts`) нормализует контакты (телефон — по последним десяти цифрам) и связывает заявки в группы; слияние (`action: merge_lead`) переносит заметки и задачи в самую раннюю заявку, дозаполняет пустые поля и отправляет дубль в корзину — безвозвратно ничего не удаляется. Кнопка «Стал клиентом» заводит карточку в разделе «Клиенты» и переводит сделку в «Выиграны».

**Клиенты** (`AdminClients.tsx` + `api/admin/clients.ts`, миграция 0032) — работа после выигранной сделки: договор со сроком и файлом, чек и день выставления счёта, границы «что входит — что не входит», следующее касание, часовой пояс клиента, доступы чек-листом, памятки и таблица месяцев (отправлен ли отчёт + расход, заявки, продажи, выручка; цена заявки считается). Светофор риска: неотправленный отчёт за прошлый месяц (после 10-го числа — до него это нормальный срок на сбор цифр), кончающийся договор, просроченное касание, выросшая больше чем на треть цена заявки. **Паролей раздел не хранит намеренно** — только факт наличия доступа; пароли должны жить в менеджере паролей, а не в вебе под одним общим паролем. Связь с заявкой — `clients.lead_id` под уникальным частичным индексом: двух клиентов из одной сделки создать нельзя.

**Финансы** (`AdminFinance.tsx` + `api/admin/finance.ts`, миграция 0033) — счета, свои расходы, часы по клиентам. «Цели и деньги» — про план, этот раздел про факт. Кнопка «выставить за месяц» создаёт счета всем активным клиентам с заполненным чеком и пропускает тех, у кого счёт за этот месяц уже есть. **«Просрочен» нигде не хранится** — это `status = 'issued'` и `due_at` в прошлом; хранимый статус пришлось бы пересчитывать по таймеру. Ставка налога задаётся вручную. Часы против чека дают ставку в час по клиенту. Поля `number` и `requisites` заложены под будущую выгрузку счёта документом — пока не используются.

**Цели и деньги** (`AdminGoals.tsx` + `api/admin/goals.ts`, миграция 0024) — план на месяц, кольца выполнения, прогноз по текущему темпу.

**Воронка** (`AdminAttribution.tsx`, `AttributionCharts.tsx` + `api/admin/attribution.ts`) — ступени с конверсиями, динамика по дням, сравнение с прошлым периодом, когорты, страна, устройство, сортируемая таблица и выгрузка CSV. Денежные показатели (цена лида, цена целевого, ROMI) считаются только по вручную введённым расходам в `ad_spend` (миграция 0023, `api/admin/ad-spend.ts`).

**Meta CAPI** (`AdminMetaCenter.tsx` + `api/admin/meta-center.ts`) — состояние D1 и схемы, очередь досылки, доставка за сутки и неделю, полнота сигналов по событиям, тренд качества. Кнопка «Тестовое событие» бьёт в `/api/meta-test-event`.

**Скорость** (`AdminPerformance.tsx` + `api/admin/performance.ts`) — PageSpeed Insights по всем URL из sitemap в Mobile и Desktop (нужен `PAGESPEED_API_KEY`). Строки страниц свёрнуты; открыты всегда те, что с ошибкой или проверяются сейчас. История замеров пишется в `pagespeed_history` (миграция 0030) одной строкой на день/страницу/режим и показывается средней оценкой по дням. Реальные метрики посетителей — `RealUserVitals.tsx` + `api/admin/vitals.ts` (миграция 0027).

**Отчёт за месяц** (`AdminReport.tsx` + `api/admin/report.ts`) — итоги месяца с сравнением с предыдущим, копированием текстом и печатью.

**Статьи** и **Кейсы** — один экран `Admin.tsx` с фильтром раздела; принадлежность к кейсам определяет категория `Кейсы`. Рядом: календарь публикаций (`ArticleCalendar.tsx`, в сетку попадают только материалы с точной `publishedAt`), метка «давно не обновлялась» (полгода без правок, черновиков не касается), окупаемость публикаций (`ContentPerformance.tsx` + `api/admin/content-stats.ts`), SEO-подсказки (`SeoAssistant.tsx`), история версий (`api/admin/article-versions.ts`), автосохранение черновика редактора в localStorage.

**Тексты сайта** (`AdminContentControl.tsx`, `AdminFaqControl.tsx` + `api/admin/site-sections.ts`, миграция 0013) — редактирование реального текста React-страниц с живым предпросмотром, черновиками, публикацией и историей версий. Порядок основных блоков зафиксирован.

**Медиатека** (`AdminMedia.tsx` + `api/admin/media.ts`) — листает и меняет только префикс `uploads/`. Папки живут в ключе объекта: `uploads/<папка>/<дата>/<файл>`; старые загрузки `uploads/<дата>/<файл>` считаются файлами без папки (`_lib/media-folders.ts`). Пустая папка существует как объект-метка `.keep`. Перенос файла — это copy+delete в R2, то есть смена публичной ссылки, поэтому файлы, на которые ссылаются публикации, нельзя ни переносить, ни удалять. Alt-тексты хранятся в D1 (`media_alt`, миграция 0031), а не в метаданных R2: объектное хранилище не умеет менять `customMetadata` на месте, пришлось бы перезаливать файл и менять ссылку. При переносе файла подпись едет за ним, при удалении удаляется.

**Проверка** (`AdminHealth.tsx` + `api/admin/health.ts`) — серверные проверки (D1, миграции, R2, приём заявок, Telegram, Meta CAPI, sitemap, RSS) под единым светофором. Блок «пиксели в этом браузере» в светофор **не входит намеренно**: на `/admin` пиксели не загружаются специально, и их «внимание» — норма.

## Миграции D1

Нумерованные файлы в `migrations/`, раннера нет — владелец применяет их вручную по порядку в консоли D1. Поэтому действует правило: **раздел без своей миграции не падает и не показывает нули, а объясняет себя**. ## Сквозное правило: не выдумывать числа

Деньги, конверсии и прогнозы показываются только там, где под ними есть введённые данные. Расход, доход и окупаемость никогда не подставляются «примерно». Разные валюты не суммируются нигде — курсов в системе нет, а придуманный курс превращает прибыль в фантазию. Если считать нечего, раздел пишет, чего именно не хватает, а не рисует ноль.

## Грабли

- ВАЖНО: CSP собирается в `_middleware.ts` (`buildCsp()`). Любой новый сторонний скрипт/пиксель/embed требует добавления в `script-src`/`connect-src`/`frame-src` там же, иначе он молча не заработает только в production. Самая частая причина «в dev работает, в prod нет».
- HTML статей всегда через санитайзеры; их ТРИ и списки должны совпадать: `functions/_lib/sanitize.ts`, `src/app/utils/sanitizeHtml.ts`, конфиг в `scripts/generate-pages.js`.
- Алиас `@/` → `src/` (vite.config.ts). `figma:asset/...` — наследие Figma Make; для новых ассетов использовать обычные импорты.
- Смоук-тесты `test:meta-capi` проверяют наличие точных строк в исходниках — при рефакторинге трекинга они могут упасть на переименовании; это сигнал обновить и код, и тест осознанно.
- Код в статьях — только через блок «Код» редактора (содержимое экранируется). Вставка кода в «HTML (fallback)» молча вырежется санитайзером.
- В локальном Vite нет D1 и R2: разделы админки, которым нужна база, показывают заглушку. Проверять их можно только в Preview или Production. Vite-плагин в `vite.config.ts` подменяет только API статей, локальный пароль по умолчанию — `admin`.
- Перезагрузка `/admin` разлогинивает: пароль живёт в памяти вкладки. После деплоя браузер продолжает крутить старый JS-чанк, пока страницу не перезагрузят, — новый раздел в меню появится только после этого.

## Качество интерфейса

Все новые и изменённые экраны проходят обязательный mobile-first UI quality gate из `docs/UI_QUALITY_CHECKLIST.md`. Проверять нужно не только общий макет, но и микродетали и открытые состояния: списки, поля, попапы, фокус, ошибки, disabled/loading, overlay/z-index, touch targets и адаптивность от 320 px. Публичные системные `<select>` и стрелки числовых полей, выбивающиеся из дизайна, не считаются готовым UI.

Светлая и тёмная темы равноправны: контраст текста проверен в обеих, правка одной без проверки второй считается незаконченной.

## Автономность и разрешения

Пользовательская команда на изменение, запуск или выкладку считается достаточным разрешением на все обычные действия внутри указанной задачи. Не задавать промежуточные вопросы и не просить отдельное подтверждение для локального редактирования, запуска или остановки dev-сервера, установки уже объявленных зависимостей, сборки, тестов, typecheck, `git add`, `git commit`, синхронизации ветки, `git push` и штатного деплоя.

- «Запусти localhost» или «запусти локальный сервер» — сразу запустить `pnpm dev` (либо подходящую команду проекта) в фоне, проверить HTTP-ответ и вернуть рабочий URL. Не спрашивать разрешение на запуск или открытие localhost.
- «Деплой в main» или «задеплой в main» — это явное разрешение проверить изменения, выполнить необходимые build/test, добавить относящиеся к задаче файлы, создать commit, синхронизировать `main`, отправить изменения в `origin/main` и проверить штатный production deploy. Не спрашивать отдельное подтверждение на каждом шаге.
- Если действие названо прямо (`commit`, `push`, `deploy`, удаление точно указанного объекта), считать его подтверждённым в указанном scope.
- Миграции D1 применяет владелец: давать SQL готовыми командами по одной, а не одним блоком.
- Действия, меняющие реальные данные владельца или уходящие наружу (слияние заявок, перевод сделки в клиента, отправка тестового события в Meta), выполняет владелец — их можно подготовить и объяснить, но не нажимать за него.
- Вопрос задавать только при объективной невозможности продолжить: отсутствует критически важный секрет или доступ, обнаружен конфликт чужих изменений, цель реально неоднозначна либо действие затрагивает данные или системы вне обозначенного scope.

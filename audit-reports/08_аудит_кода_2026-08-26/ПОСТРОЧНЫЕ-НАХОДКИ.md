### `d1.ts` (263 строки) — 🟠 два серьёзных вопроса

**1. Дату публикации нельзя изменить — она заблокирована дважды.**

Строка 221:
```ts

```
Строки 206–208:

**2. Сохранение статей удаляет всё, чего нет во входящем списке.**

Строки 251–256: всё из `existingArticles`, чего нет в присланном наборе,

Мелочь: `updateSet.unshift('id = excluded.id')` (строка 210) — при конфликте по

### `jsonbin.ts` (380 строк) — 🔴 здесь лежит сломанная функция админки

#### 🔴 Дата публикации не сохраняется. Отложенная публикация не работает.

`applyFreshnessMetadata`, строка 222:

```ts
const publishedAt = previous?.publishedAt || previous?.updatedAt || article.publishedAt || nowIso;
```

Приоритет: старая дата → **время последней правки** → и только потом то, что
ввёл владелец. А `updatedAt` проставляется при каждом сохранении (строки 228 и
237). Значит после первого же сохранения у статьи всегда есть `updatedAt`,
и **введённая в админке дата публикации не может примениться никогда**.

Если у статьи не было `publishedAt`, но был `updatedAt`, датой публикации
станет время последней правки — то есть вместо введённой даты подставится
посторонняя.

Замок стоит трижды, в двух путях сохранения:

| Где | Что делает |
|---|---|
| `jsonbin.ts:222` (`applyFreshnessMetadata`) | общая функция, работает для **обоих** хранилищ |
| `d1.ts:221` | `previous?.publishedAt \|\| article.publishedAt` — второй замок |
| `d1.ts:207` (SQL) | `COALESCE(articles.published_at, excluded.published_at)` — третий |

**Что видит владелец.** В `Admin.tsx:1730` есть поле выбора даты и времени,
в `Admin.tsx:1718` — подпись «(запланирована на …)». То есть отложенная
публикация — заявленная функция. Владелец ставит дату, жмёт сохранить,
получает «успешно» — и дата тихо откатывается. Работает это только для
совершенно новой статьи, у которой раньше даты не было вообще.

Календарь публикаций (`ArticleCalendar`) строится на точной `publishedAt` —
он показывает даты первого сохранения, а не то, что задумал владелец.

**Как чинить:** поменять приоритет на «введённое значение важнее старого»
(`article.publishedAt || previous?.publishedAt || nowIso`) во всех трёх местах.
Пустая строка из редактора остаётся falsy, поэтому статья, у которой дату не
трогали, сохранит старую. Правку не вношу молча — это изменение поведения
данных, вынес в решения владельца.

### `admin-totp.ts` (185 строк) — 🟢 норма, алгоритм разобран построчно

Криптографию проверял отдельно, потому что она написана вручную:

- динамическое усечение (строки 88–92): у SHA-1 дайджест 20 байт, `offset`

Мелочь: комментарий обещает допуск ±30 секунд, фактически окно из трёх шагов —

### `admin-2fa.ts` (173 строки) — 🟠 резервный код можно использовать дважды

Для TOTP отметку сделали атомарной и это прямо прокомментировано —
`claimTotpStep` (строки 153–158):

```sql
UPDATE admin_2fa SET last_step = ? WHERE id = 1 AND last_step < ?
```

А для резервного кода — нет. `consumeBackupCode` (162–172):

```ts
const remaining = state.backupCodeHashes.filter((item) => item !== hash);
await env.DB.prepare('UPDATE admin_2fa SET backup_codes = ? WHERE id = 1')
  .bind(JSON.stringify(remaining)).run();
return true;
```

Прочитали → отфильтровали → записали, без условия. Два одновременных входа
с **одним и тем же** резервным кодом оба прочитают состояние, оба увидят код
в списке, оба запишут и **оба вернут `true`**. Код, который по описанию
одноразовый («повторно им уже не войти»), сработает дважды.

Плюс `state` приходит от вызывающей стороны и к моменту записи может устареть.

**Как чинить:** сделать как с TOTP — обновлять с условием на прежнее значение
и возвращать результат по числу изменённых строк:

```sql
UPDATE admin_2fa SET backup_codes = ? WHERE id = 1 AND backup_codes = ?
```

Практическая опасность невелика (нужно знать живой резервный код и попасть в
гонку), но заявленная гарантия сейчас не выполняется.

Отдельно, но это **описанный компромисс, а не ошибка**: при недоступной D1
`isAdmin2faEnabled` возвращает `false`, то есть вход идёт по одному паролю.
В шапке файла объяснено — обратный вариант запирал бы владельца снаружи.

### `form-guard-stats.ts` (105 строк) — 🟡 один день может соврать нулём

Файл сам ставит себе правило: «Выдавать усечённое число за точное нельзя».
Но есть путь, где именно это и происходит.

Строки 74–77 отмечают день неполным так:

```sql
UPDATE form_guard_daily SET throttled = 1
WHERE day = ? AND reason = ? AND throttled = 0
```

`UPDATE` меняет строку, только если она уже есть. Если суточный бюджет записей
исчерпан **раньше**, чем для этой причины появилась первая строка, обновлять
нечего — строка не создастся, и причина за этот день не будет видна вообще.
Не «не меньше N», а пусто.

Сценарий узкий (нужен поток отказов одного вида, начавшийся после исчерпания
бюджета другими), но он ровно про то, от чего файл защищается.

#### 🟠 Дедупликация заявок перестанет работать после 500 заявок

Строки 195–197:

```sql
SELECT id, email, phone, telegram_username, submissions_count
FROM leads WHERE deleted_at IS NULL ORDER BY id DESC LIMIT 500
```

Повторная заявка ищется **только среди последних 500**. Как только активных
заявок станет больше, старый контакт, написавший снова, создаст **дубль**
вместо «поднятия» существующей записи со счётчиком.

Это заявленное поведение из CLAUDE.md («повторная заявка поднимает существующую
со счётчиком, а не создаёт дубль»), и оно отключится само, тихо, по достижении
порога. Заодно: 500 строк вычитываются из базы **на каждую заявку**.

#### 🟠 Один и тот же человек не склеится, если написал телефон по-разному

`contactKeys` (90–96) нормализует телефон как «все цифры подряд»:

```ts
phone: String(phone || '').replace(/\D/g, '')
```

`+7 999 123-45-67` → `79991234567`, а `8 999 123-45-67` → `89991234567`.
Это **разные ключи**, дедупликация не сработает.

Показательно, что в поиске дублей внутри CRM (`leadDuplicates.ts`) телефон
сравнивают по **последним десяти цифрам** — то есть правильный подход в проекте
уже есть, но в приём заявок он не попал. Две части системы считают «тот же
человек» по-разному.

### `meta-outbox.ts` (349 строк) — 🟡 одна недоработка счётчика попыток

Разобрал самое важное — захват записей (247–257). `UPDATE ... WHERE id IN

#### 🟡 Счётчик попыток не сохраняется в момент захвата

возраст события — шесть суток.

Лечится одной правкой: `attempts = attempts + 1` прямо в захватывающем UPDATE.

### `article-page.ts` (239 строк) — 🟠 две находки

Сначала снял подозрение из прошлого файла: черновики и будущие публикации
отсекаются на строке 179 (`filterVisibleArticles`) **до** рендера, так что
жёсткий `robots: index, follow` в `seo.ts` до них не доходит. Чисто.

Проверил и то, что описано в CLAUDE.md как больное место: страница статьи
действительно не подменяется оболочкой главной, canonical ставится через
HTMLRewriter, слеш уходит в 301. Всё так.

#### 🟠 Ответ зависит от User-Agent, но `Vary: User-Agent` не выставляется

Боту отдаётся `renderArticleHtml` (голая SEO-разметка), человеку — оболочка SPA.
Развилка — на `isBotRequest`, то есть **по заголовку User-Agent**.

При этом ответ для бота уходит с `Cache-Control: public, s-maxage=300,
stale-while-revalidate=900` (`CACHE_CONTROL.botArticle`) и **без** заголовка
`Vary: User-Agent`.

Любой общий кэш — CDN, корпоративный прокси — имеет полное право отдать
сохранённый ответ следующему запросу того же URL независимо от User-Agent.
То есть человек может получить голую SEO-страницу без стилей и без React,
а бот — оболочку SPA.

Это не теория, а прямое требование HTTP: содержимое зависит от заголовка
запроса → этот заголовок обязан быть в `Vary`. Лечится одной строкой.

#### 🟠 Заголовки копируются на уже переписанное тело

`getArticleShell`, строка 78:

```ts
const source = await sectionShell.text();
const neutral = source.replace(...);
return new Response(neutral, { status: 200, headers: sectionShell.headers });
```

Тело прочитано, изменено и отдано **со старыми заголовками**. Там остаются
`Content-Length` от исходного файла и, что хуже, возможный
`Content-Encoding: gzip` — при том что `.text()` уже распаковал содержимое.
Браузер, поверив заголовку, попытается распаковать обычный текст.

Ветка запасная (срабатывает, только когда статью опубликовали между сборками),
поэтому в обычной жизни не проявляется. Но именно поэтому и не заметят.

Рядом, для сравнения, сделано правильно: на строке 219 ответ собирается со
своим свежим набором заголовков.

#### 🟡 При сбое хранилища человек может получить 404 на существующую статью

Строка 183: при ошибке чтения человеку отдаётся

### `page-lock-notify.ts` (196 строк) — 🟢 норма, проверял придирчиво

Здесь был мой главный подозреваемый, и он не подтвердился. Разбираю, потому
что случай поучительный.

Форма позволяет оставить что-то одно: почту, телефон или телеграм. В `INSERT`
незаполненные поля уходят пустыми строками, а стоит `ON CONFLICT DO NOTHING`.
Обычный уникальный индекс по `(path, email)` считал бы **всех**, кто оставил
только телефон, одним и тем же контактом — второй такой человек молча получил
бы «вы уже в списке» и потерялся.

Проверил миграцию 0035: индексы сделаны **частичными**, каждый следит только
за заполненным полем:

```sql
CREATE UNIQUE INDEX idx_page_lock_subscribers_email
  ON page_lock_subscribers(path, email) WHERE email <> '';
```

Старый непартиальный индекс из 0034 при этом явно удаляется. И до применения
0035 всё тоже верно: без её колонок форма показывает только почту, значит
пустых почт не бывает. Корректно в обоих состояниях схемы — редкий уровень
аккуратности.

Остальное тоже на месте: ловушка для ботов возвращает «успех» (бот не узнает,
что его отсекли), подпись формы проверяется, контакты принимаются только на
действительно закрытой странице, телефон не достраивается выдуманным кодом
страны, в Telegram сообщение уходит без `parse_mode` — то есть разметка в
чужом вводе безопасна.

### `articles.ts` (120 строк) — 🟠 публичный обход кэша (связано с расходом лимитов D1)

Строка 30:

```ts
const bypassCache = url.searchParams.has('_') || url.searchParams.get('cache') === 'no-store';
```

**Любой** запрос с параметром `_` или `cache=no-store` минует кэш и идёт прямо
в базу. Проверки, кто спрашивает, нет — эндпоинт публичный.

Что это значит на практике: запрос вида `/api/articles?_=1`,
`/api/articles?_=2`, `/api/articles?_=3` заставляет базу **каждый раз** читать
все статьи целиком. Кэш при этом не спасает по определению — его же и просят
пропустить.

Оба параметра нужны по делу: `?_=<время>` использует админка, `?cache=no-store` —
сборка (`scripts/config.js`). Но обход рассчитан на своих, а доступен всем.

Разумно: оставить обход только для запроса с паролем администратора
(`X-Admin-Password` тут уже проверяется в соседних эндпоинтах) либо для
запроса со стороны сборки, а публичному трафику отдавать кэш всегда.

🟡 Строка 108: `details: error.message` уходит наружу в теле ответа. Туда
попадают внутренние сообщения вроде «D1 articles are unavailable and no
last-known-good D1 snapshot can be read» или сырая ошибка SQLite. Логировать —
да, отдавать публично — незачем.

### `admin/vitals.ts` (131 строка) — 🔴 список самых медленных страниц был пуст. Исправлено.

Строка 74 (было):

```sql
SELECT page_path, SUM(samples) AS samples, ... FROM web_vitals_daily
GROUP BY page_path
HAVING samples >= 3
```

`samples` — это **одновременно** колонка таблицы и псевдоним результата.
В `HAVING` SQLite выбирает **колонку**, а не сумму. Проверил на живом SQLite,
а не по памяти:

| Запрос | Результат |
|---|---|
| `HAVING samples >= 3` | только `b` (5) — **`a` с суммой 4 отсеяна** |
| `HAVING SUM(samples) >= 3` | и `a` (4), и `b` (5) |

Что это значило на практике. Порог «не меньше трёх выборок» применялся не к
сумме за период, а к значению **одной суточной строки**. Страница, у которой
по 2 посетителя в день на протяжении месяца (в сумме 60 замеров), отсеивалась
как «мало данных» и в список не попадала никогда.

При вашем трафике (3–12 посетителей в сутки) суточных строк с тремя и более
выборками почти не бывает — то есть таблица «самые медленные страницы» была
пустой практически всегда. Раздел «Скорость» показывал, что всё в порядке,
просто потому что не показывал ничего.

**Исправлено:** `HAVING SUM(samples) >= 3`. Заодно убрана голая колонка `metric`
из выборки с группировкой — она там была лишней (её и так фиксирует `WHERE`).

Проверил, нет ли такого же приёма в других запросах проекта — больше нигде нет.

#### 🟠 `visitors` в отчёте за месяц — это сумма суточных значений

`report.ts:87`:

```sql
SELECT COUNT(*) AS total FROM visitor_hashes_daily WHERE day >= date(?) AND day <= date(?)
```

В таблице одна строка на **день и посетителя**, поэтому за месяц постоянный
читатель посчитается столько раз, сколько дней заходил. Человек, заходивший
двадцать дней, даст двадцать «посетителей».

Это то же самое, что я отметил в `stats.ts` про `uniques7`, но здесь искажение
кратно больше: неделя против месяца. И это **отчёт, которым подводят черту**.

Причина та же и неустранимая при нынешней схеме: отпечаток содержит дату
(`sha256(ip|ua|day|salt)`), поэтому у одного человека каждый день новый хеш.
Посчитать уникальных за период по этим данным нельзя в принципе.

Значит, честный выход один — назвать цифру тем, чем она является:
«визитов по дням, суммарно», а не «посетителей».

четырнадцатый случай обёртки вокруг колонки.

## `functions/_lib/rate-limit.ts` + обе формы

🔴 **При 429 заявка терялась.** Ограничитель отдавал
`{ error: 'Too many requests', scope }` — **без признака «можно повторить»**.
Формы считают отказ окончательным, если сервер не сказал обратного, поэтому
человек видел английское «Too many requests», а заявка выбрасывалась: ни в
очередь, ни на сервер она уже не попадала.

429 временный по определению — рядом в том же ответе стоит `Retry-After`.
Лимит на заявки — двадцать за десять минут **с одного адреса**, и упереться в
него может не только бот: за одним адресом сидят все абоненты мобильного
оператора. Плюс это складывалось с другой находкой того же дня — застрявшая в
очереди заявка пробовалась на каждой загрузке страницы и сама выедала лимит.

**Исправлено с двух сторон:** сервер теперь отдаёт `retryable` и `retry_after`,
а формы и очередь пользуются общим правилом `isRetryableLeadStatus`
(408, 429 и 5xx) и не зависят от того, что ответит сервер.

🟡 Заодно: `getRateLimitProfile` искал профиль обычным поиском по объекту. Для
ключа `constructor` вернулась бы функция, порог стал бы `undefined`, сравнение
`nextCount > undefined` — всегда ложным, и **ограничитель молча выключился бы**.
Область вызова сейчас всегда своя, эксплуатировать нечем, но проверка стоит
одну строку.

## Ссылки на статьи для поисковика — проверено отдельно

# Проход 6 — админка: числа и даты

## `AdminGoals.tsx` + `api/admin/goals.ts`

🔴 **Цель по выручке ошибалась в сто раз.** Поля «Выручка» и «Потолок расхода»
вырезали из ввода всё, кроме цифр и точки:

```
'1 500,50'.replace(/[^\d.]/g, '')  →  '150050'
```

Запятая просто исчезала. Это ровно то число, от которого считаются кольца
выполнения и прогноз всего раздела «Цели и деньги», — то есть неверной
становилась вся картина месяца.

**Исправлено:** оба поля переведены на `AdminDecimalInput`, тот же, что уже
стоит в «Финансах» и «Клиентах». Поля «Заявки» и «Целевые заявки» не тронуты:
там `replace(/\D/g, '')` — правильная чистка для целых.

🟠 **На сервере тот же разбор ломался на другом формате.** Он менял **первую**
запятую на точку и вырезал остальное, поэтому `1,234.56` превращался в
`1.234.56` и обнулялся. Проверено запуском на шести форматах:

| Ввод | Старый разбор | Новый |
|---|---|---|
| `1500.50` | 1500.5 | 1500.5 |
| `1 500,50` | 1500.5 | 1500.5 |
| `1,234.56` | **0** | 1234.56 |
| `1.234,56` | **0** | 1234.56 |
| `$1,234.56` | **0** | 1234.56 |

Теперь используется общий `parseMoney` — уже четвёртый раздел, сведённый на
одну реализацию.

## Проверено, норма — и это важно

**Правило «не выдумывать числа» соблюдается сквозным образом.** Проверена вся
цепочка от вычисления до экрана:

1. Деления защищены не от «ошибки», а по смыслу: ROMI считается только при
   `spend > 0`, цена лида — только при непустом числе заявок, ширина полосы
   когорты — с `Math.max(..., 1)`.
2. Когда считать нечего, возвращается `null`, а не ноль.
3. Форматтеры (`formatNumber`, `formatPercent`, `formatMoney`) рисуют `null`
   как «—», а не как «0».

То есть пустое место на экране означает «нет данных», и это невозможно спутать
с настоящим нулём. Так и должно быть.

**Даты в CRM разобраны верно.** Проверена вся цепочка: сервер приводит любую
дату к полному ISO с `Z` (`normalizeDateTime`), поле «когда» переводит её в
местное время и обратно (`toDateTimeLocal` / `toUtcIso`), а проверка «просрочено»
читает ту же строку с `Z`. Смещения часового пояса здесь нет.

**«Что изменилось со вчера»** сравнивает два последних **завершённых** дня —
сегодняшний ещё идёт, и сравнивать его не с чем. Блок вообще не появляется,
пока все три показателя нулевые, так что стены нулей не бывает.

## Разбор сумм в остальных местах админки

- **Расходы** (`AdminAdSpend`) — поле хранит строку как есть и отдаёт её на
  сервер, где работает общий разбор. Правильный образец.
- **Сумма сделки** (`AdminLeads`) — чистит ввод на месте; формат `1,234.56`
  сервер отклоняет с понятной ошибкой, а не записывает молча ноль. Оставлено:
  честный отказ лучше тихой порчи.

несогласованность стоит держать в голове.

# Проход 9 — конвейер сборки контента

## `scripts/fetch-articles.js`

🟠 **Единичный сбой сети ронял сборку статей.** Повторы при сбое были только у
JSONBin, а публичный API опрашивался **одной попыткой**. При этом он
опрашивается со сборки на Cloudflare и обращается к тому же самому сайту, где
единичный сбой обычен: холодный старт, гонка с предыдущим деплоем.

Без повторов такой сбой сразу уводил сборку на запасной источник, а в режиме D1
(где JSONBin намеренно не читается) — прямо на снимок прошлой сборки. При
включённом `REQUIRE_FRESH_ARTICLES` сборка на этом просто падала.

**Исправлено:** повторы вынесены в общую обёртку и применены к обоим
источникам. Повторяется только неудача самого запроса. Пустой или негодный
список по-прежнему считается **ответом, а не сбоем**, и проверяется отдельно —
правило «пустой список из D1 — это канон» не тронуто.

Проверено: семь тестов `fetch-articles.test.js` проходят, включая «в режиме D1
JSONBin не вызывается после отказа публичного API» и «строгая свежесть валит
сборку на запасном источнике».

Проверено, норма: снимок, записанный из запасного источника, помечается своим
именем и на следующей сборке **не считается авторитетным** — то есть однажды
подставленный запасной контент не закрепляется навсегда.

## `scripts/site-content-sync.js`

Проверено, норма — и главное здесь проверено запуском, а не чтением.

**Правила слияния текстов совпадают у сайта и у сборки.** Это заявленный
инвариант: живая страница и сгенерированный SEO-HTML обязаны одинаково
разрешать частичную правку из админки. Реализации две, и написаны они
по-разному: сайт проверяет наличие ключа через `key in base`, сборка — через
`hasOwnProperty`. Первая форма видит и унаследованные свойства, поэтому
расхождение было бы возможно.

Прогнал обе реализации на шести входах, включая `toString`, `valueOf` и
`hasOwnProperty` в качестве ключей правки:

```
расхождений: 0
```

Инвариант держится. Разницу в форме проверки оставляю заметкой: она ничего не
ломает сегодня, но это ровно то место, где две копии одного правила могут
однажды разойтись.

Ещё проверено:

- защита от подмены прототипа (`__proto__`, `constructor`, `prototype`) стоит в
  **обеих** реализациях;
- ответ «опубликованной правки нет» очищает устаревшую запись снимка, а не
  оставляет её жить;
- при полном отказе сети снимок **не перезаписывается**, а при частичном
  успехе обновляются только ответившие разделы;
- версия формата снимка проверяется, поэтому старые ручные заготовки не могут
  просочиться в production-HTML.

Пятнадцать тестов трёх файлов синхронизации проходят.

## Проверено, норма

**`_routes.json`** выводит из-под функций только каталоги статики
(`/assets`, `/fonts`, `/images`). Поэтому `_middleware.ts` для них не работает —
и ровно поэтому те же заголовки продублированы в `public/_headers`. Связку
проверяет тест «bypassed static assets retain security and cache headers».

**`_redirects`** содержит только то, что нужно: доступ к `articles.seed.json` и
канонический редирект на www. Общего фолбэка на index нет **намеренно** — он
создавал бы soft-404; правило `/api/article` убрано, потому что функция уже
отвечает 308, а вторая запись с кодом 302 ей противоречила.

**`vite.config.ts`** — сборка разложена по чанкам осмысленно (react, motion,
иконки одним файлом вместо двадцати по 300 байт), манифест включён ради
пораутного `modulepreload`. Плагин локального API статей помечен `apply: 'serve'`
и в production-сборку не попадает вовсе, вместе с локальным паролем по умолчанию.

**`index.html`** не содержит ни пикселей, ни preconnect: счётчики грузятся из
`consent.ts` после согласия, а preload картинок героя расставляет генератор
пораутно — общий preload заставлял все 28 страниц тянуть чужую картинку.

# Проход 8 — данные кейсов

## 🔴 `/cases?from=constructor` роняла страницу целиком

Значение `?from=` приходит прямо из адреса и использовалось как ключ **трёх**
карт обычным поиском по объекту. Такой поиск находит и унаследованные свойства:
для `constructor` возвращалась функция `Object` вместо `undefined`, дальше у неё
читалось `preset.sources.filter(...)` — и страница падала во время отрисовки.

**Подтверждено на живом сайте, а не выведено из кода.** До правки:

```
консоль:  TypeError: Cannot read properties of undefined (reading 'filter')
          React Router caught the following error during render
на экране: «Страница не загрузилась»
карточек:  0
```

После выкладки, тот же адрес и ещё два ключа:

| Адрес | Карточек | Экран сбоя | Консоль |
|---|---|---|---|
| `?from=constructor` | 2 | нет | пусто |
| `?from=__proto__` | 2 | нет | пусто |
| `?from=toString` | 2 | нет | пусто |

**Это третий случай одной и той же ошибки в проекте.** Раньше так же чинились
`FROM_ALIASES` в навигации (там падала любая страница с `?from=`) и профили
ограничителя частоты (там молча отключалась защита). Здесь — самый жёсткий
вариант: белый экран вместо витрины кейсов.

Все три карты кейсов (`ENTRY_PRESETS`, `CASE_BACK_TARGETS`, `CASE_CATALOG_META`)
теперь ищутся через отдельные функции с честным типом возврата.

🟡 Заодно закрыто последнее место этого класса на публичном сайте: подпись
источника кейса (`SOURCE_LABELS`) берёт ключ из данных админки, и значение
`constructor` вернуло бы функцию — React упал бы, пытаясь отрисовать её текстом.

## Сквозной поиск по всему публичному сайту

После правки прогнал поиск по всем картам, к которым обращаются переменным
ключом. Четырнадцать мест, разобраны все:

- **три** — уже закрыты этой правкой;
- **одно** — закрыто раньше (`FROM_ALIASES`);
- **шесть** ищутся по пути с ведущей косой чертой (`/constructor` ≠
  `constructor`) — подмена туда не проходит;
- **четыре** используют внутренние перечисления и числовые индексы.

Мест этого класса на публичном сайте больше не осталось.

## `caseCatalog.ts` — проверено, норма

Правило «данные из админки главнее заготовки» соблюдено буквально:

```
if (article.caseData !== undefined) return article.caseData;
```

То есть **пустой** объект из CMS выигрывает у заготовки в коде — удалённые
цифры не могут вернуться на сайт через запасной каталог. Это ровно то же
правило, что и «пустой список статей из D1 — это канон», и здесь оно записано
явно.

`getCaseDisplayTitle` поднимает первую букву только там, где действительно
срезал префикс «Кейс: », и не трогает чужие написания.

# Проход 12 — CSS и проверка админки

## 🟡 Индикатор «идёт синхронизация» ничего не показывает

В `admin-ui.css` правило для значка синхронизации в точном предпросмотре:

```css
.admin-root .admin-site-preview__sync.is-pending {
  border-color: color-mix(in srgb, var(--adm-accent) 40%, transparent);
  color: var(--adm-accent);
}
```

Переменной `--adm-accent` **не существует**: проверено по всем файлам стилей и
по всему коду — ноль присвоений. В палитре админки акцент называется
`--adm-primary`.

Неопределённая переменная внутри `color-mix()` делает всю функцию
недействительной, поэтому **оба объявления отбрасываются**. Состояние
«синхронизация идёт» выглядит ровно так же, как обычное, — владелец не видит,
что предпросмотр обновляется.

**Не исправлял намеренно.** Правка вернула бы значку подсветку, то есть
скриншот «до» и «после» разошёлся бы, а это прямо запрещено правилом о дизайне.
Замена одного слова (`--adm-accent` → `--adm-primary`) — решение на секунду,
но принимать его должен владелец.

## CSS — проверено, норма

Двадцать восемь тысяч строк в одиннадцати файлах:

| Проверка | Результат |
|---|---|
| Баланс фигурных скобок | сбалансированы во **всех** файлах |
| Повторяющиеся селекторы | разобраны вручную, случайных дублей нет |
| Переменные без определения | одна (описана выше) |

Повторы селекторов оказались обычной каскадной записью: первое правило задаёт
раскладку, второе — общие с соседом сброс и переход. Разных свойств, взаимного
перекрытия нет. Проверены `.cases-back-link`, `.ww-scroll-trail__route-sheen`,
`.case-article-back`, `.cases-empty-state`, `.cases-filter-apply`.

Переменные, показавшиеся неопределёнными, при проверке оказались заданными:
`--ths-angle` и `--ww-ang` объявлены через `@property` (с типом и начальным
значением), `--pl-tone` и `--adm-bar` — в блоках с состояниями,
`--radix-select-*` ставит Radix во время работы, `--text-*` и
`--tw-gradient-stops` приходят из Tailwind.

## Админка — четыре проверки, все чистые

**Подмена ключа в админке невозможна.** Четырнадцать мест, где карта ищется
переменным ключом, разобраны: ключи приходят из внутренних перечислений или из
серверных констант. Ключевое проверено до конца: `lead_activity.type` пишется
только из карты `ACTIVITY_TYPES` с фиксированным набором значений, поэтому
`ACTIVITY_LABELS[activity.type]` не может получить `constructor`.

**Защита медиатеки работает.** Файл, на который ссылается публикация, нельзя ни
удалить, ни перенести — проверено по всей цепочке: компонент получает статьи из
`Admin.tsx`, тот берёт их через админский эндпоинт, а он отдаёт **полные**
статьи с содержимым (не сводки). Значит проверка `content.includes(...)`
работает на настоящем тексте, а не на пустой строке.

Отдельно проверил последствие своей же правки: после кодирования ссылок R2
адрес файла с кириллической папкой изменился, и совпадение по URL для старых
статей перестало бы срабатывать. Проверка двойная — вторым условием идёт
совпадение по ключу объекта, который остался прежним. Защита не сломалась.

**Доска CRM.** Перетаскивание карточки делает оптимистичное обновление,
откатывает его при ошибке, передаёт ожидаемую версию записи (защита от
одновременной правки) и перечитывает данные после успеха. Неизвестный этап —
например, после ручной правки в базе — не роняет карточку и не прячет её, а
показывается в «новых».

🟡 Заметка: в медиатеке создание папки и запасное копирование ссылки сделаны
системным `prompt()`. У админки есть свой слой уведомлений и подтверждений
(`notify`, `confirmAsk`), но диалога с полем ввода в нём нет. Та же история, что
и с `alert()` в публичных формах, — вопрос к владельцу, не поломка.

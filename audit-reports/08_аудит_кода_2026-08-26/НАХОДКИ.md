## A. Настоящие ошибки

### A1. Офлайн-очередь заявок не может доставить ни одной заявки 🔴

**Файлы:** [leadRetryQueue.ts](src/app/utils/leadRetryQueue.ts),
[lead.ts:694](functions/api/lead.ts:694), [turnstile.ts](functions/_lib/turnstile.ts)

Цепочка:

1. Заявка не ушла (нет сети) → `queueLeadForRetry` кладёт **весь payload вместе
   с `turnstile_token`** в localStorage.
2. Через час/день `flushLeadQueue` отправляет тот же payload с тем же токеном.
3. Токен Turnstile одноразовый и живёт минуты — это написано в шапке
   `_lib/turnstile.ts` прямым текстом.
4. `/api/lead` проверяет токен **до** записи в базу → `invalid_token` → **403**.
5. `flushLeadQueue` удаляет из очереди только при `res.ok` → заявка остаётся
   и повторяется каждый визит трое суток, всегда получая 403.

**Итог: заявка, попавшая в очередь, не будет доставлена никогда.**
Turnstile в продакшене включён (`docs/SECURITY.md`, проверено 23.08.2026),
значит это работает прямо сейчас.

Второй путь в ту же яму: при недоступной D1 сервер отвечает `503 retryable`,
но токен уже сожжён проверкой (она идёт раньше записи) — повтор снова 403.

### A2. Временный сбой Turnstile теряет живую заявку 🔴

**Файл:** [lead.ts:699](functions/api/lead.ts:699)

`verification_unavailable` (Cloudflare не ответил или таймаут) отдаётся как
**403 без поля `retryable`**. Клиент кладёт в очередь только при
`retryable === true`, поэтому такая заявка не попадает даже в очередь —
человек видит сообщение об ошибке, заявка исчезает.

Это не бот: сама `_lib/turnstile.ts` отделяет эту причину от `invalid_token`
именно потому, что «это не признак бота».

### A3. Meta не получает тип устройства с iPhone и Firefox 🟠

**Файлы:** [lead.ts:542](functions/api/lead.ts:542),
[meta-event.ts:505](functions/api/meta-event.ts:505),
[pageview.ts:470](functions/api/pageview.ts:470)

Все три отправителя берут `device_type` только из заголовка
`Sec-CH-UA-Mobile`. Этот заголовок присылает **только Chromium**.
Safari на iPhone и Firefox его не присылают вовсе → параметр уходит пустым.

При этом в `lead.ts` уже есть `detectDevice(user-agent)` (строка 105), и его
результат кладётся в базу (`normalized.device`), но **в Meta не передаётся**.

То есть сервер знает устройство, но Meta его не получает — ровно на той
части трафика, которая для владельца важнее всего.

### A4. `win.ttq.load` без защиты от undefined 🟡

**Файл:** [consent.ts:609](src/app/consent/consent.ts:609)

```
win.ttq.load?.(tiktokId);
```

`?.` стоит на `load`, а не на `ttq`. Если `ttq` не создан — `TypeError`,
и он вылетает из `loadMarketingRuntimes()`, то есть **отравляет
`marketingLoadPromise`** уже после того, как пиксель Meta загрузился.
Весь остальной файл пишет это правильно: `win.ttq?.track?.(...)` (строка 1735).

### A5. Дубль ключа в событии Meta Lead 🟡

**Файл:** [lead.ts:529](functions/api/lead.ts:529)

`contact_method` задаётся дважды: явно и следом через спред
`...getLeadDiagnosticsContext(payload)`. TypeScript со strictNullChecks
это ловит (TS2783). Значения совпадают, поэтому поведение сейчас верное,
но конструкция хрупкая: изменение хелпера молча перезапишет явное поле.
То же с `form_id`, `form_variant`, `lead_source_page`.

## B. Разъехавшиеся связи

### B1. CSP существует в трёх местах, и они разошлись 🟠

| Где | `frame-src` содержит домены Яндекса |
|---|---|
| `functions/_middleware.ts` | **да** |
| `public/_headers` | нет |
| `scripts/generated-seo.test.js` (константа) | нет |

В `_middleware.ts` прямо в комментарии написано, что домены Вебвизора когда-то
забыли во `frame-src` и это давало ошибку CSP на каждой странице. Правку внесли
в один файл из трёх.

Тест сравнивает `_headers` с **собственной копией строки внутри теста**, а не
с `_middleware.ts`, хотя его сообщение обещает «must match the Function security
policy». Поэтому расхождение осталось зелёным.

Практический вред сейчас мал: `_headers` применяется только к
`/assets/*`, `/fonts/*`, `/images/*` (см. `public/_routes.json`), а это не
документы. Но защита от повторения не работает.

### B2. Четыре циклические зависимости 🟢

1. `hooks/useFaqContent.ts` → `pages/FAQPage.tsx` — только `import type`,
   на сборку не влияет.
2. `routes.tsx` → `cookie/CookieConsentManager.tsx` — через `React.lazy`,
   на старте не выполняется.
3. и 4. `AdminContentControl.tsx` ↔ `AdminContentPreview.tsx`.

Ни один сейчас не ломается, но первые два держатся на том, что импорт
не настоящий. Стоит знать.

## F. `package-lock.json` устарел и отменяет пины безопасности 🟠

Обнаружено при попытке `npm ci` — она **не запускается вообще**:

```
npm error Invalid: lock file's vite@6.3.5 does not satisfy vite@6.4.3
npm error Invalid: lock file's tar@7.5.16 does not satisfy tar@7.5.21
npm error Invalid: lock file's postcss@8.5.15 does not satisfy postcss@8.5.23
npm error Invalid: lock file's nanoid@3.3.14 does not satisfy nanoid@3.3.17
```

| Файл | vite | tar | postcss | nanoid |
|---|---|---|---|---|
| `package.json` (+ `overrides`) | 6.4.3 | 7.5.21 | 8.5.23 | 3.3.17 |
| `pnpm-lock.yaml` | 6.4.3 ✅ | — | — | — |
| `package-lock.json` | 6.3.5 ❌ | 7.5.16 ❌ | 8.5.15 ❌ | 3.3.14 ❌ |

Блок `overrides` в `package.json` пинит `nanoid`, `postcss` и `tar` — это
похоже на закрытие уязвимостей. `pnpm-lock.yaml` их учитывает,
`package-lock.json` — нет.

**Продакшену это сейчас не вредит:** Cloudflare Pages собирает по
`pnpm-lock.yaml`, а он в порядке. Но любой, кто поставит зависимости через
`npm`, получит именно те версии, ради замены которых `overrides` и добавляли.

**Специально не трогал.** Перегенерация локфайла — самая рискованная правка
из возможных для продакшен-сборки, а функциональной пользы она не даёт.
Решение за владельцем; варианты — в конце файла.

# Что осталось владельцу решить

### 1. `package-lock.json` (см. раздел F)

Три варианта:

- **пересобрать** — `npm install` перезапишет локфайл под `package.json`;
  `npm ci` снова заработает, пины безопасности применятся;
- **удалить** — источник истины по CLAUDE.md всё равно `pnpm-lock.yaml`,
  второй локфайл только вводит в заблуждение;
- **оставить** — но тогда стоит записать в CLAUDE.md, что он заведомо
  устаревший и ставиться по нему нельзя.

Рекомендую первый вариант, но выполнять его нужно с последующей проверкой
production-сборки — поэтому за вами.

### 2. Ценность лида в Meta (`value` / `currency`)

Сейчас в событии `Lead` они не передаются — это было осознанное решение
(в коде рядом стоял комментарий, функцию-заглушку `estimateLeadValue`
я удалил как мусор). Meta умеет оптимизироваться на ценность, но для этого
нужна **настоящая** цифра, а не оценка «750 если услуга, иначе 500».
Если появится реальная средняя ценность лида по услугам — это можно включить
честно. Придумывать не буду: правило «не выдумывать числа» в CLAUDE.md.

### 3. Тип устройства для планшетов

`Sec-CH-UA-Mobile` в Chromium отдаёт `?0` для планшета, то есть «desktop».
User-agent различает планшет точнее. Сейчас заголовок остаётся главным
(поведение для Chrome не изменилось), user-agent только заполняет пустоту.
Если хотите, чтобы планшеты в Meta считались планшетами, — можно поменять
приоритет, но это уже изменит данные по существующему трафику.

### 4. ESLint в проекте

Половина находок этого аудита — из ESLint, которого в проекте нет.
Ставил его временно и убрал за собой (`package.json` и оба локфайла
не изменились). Если добавить его постоянно, такие ошибки будут
находиться сами. Мешает то же расхождение локфайлов — сначала пункт 1.
